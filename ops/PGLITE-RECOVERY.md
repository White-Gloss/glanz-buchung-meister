# Recover an existing in-memory White Gloss database

These helpers are explicit recovery tools. They are not part of application startup or automatic deployment. Keep the existing Node process alive until a sealed snapshot has been restored and checked. Pause automatic deployment first.

1. Inspect the actual service MainPID using `scripts/rescue-live-pglite.mjs inspect --pid PID`. The helper verifies the process and opens its inspector on loopback only, then closes it. It never creates a missing PGlite instance.
2. Run `backup --pid PID` for an initial snapshot. Copy its tar and optional `auth-signing-secret.txt` into a separate root-owned backup directory (directory 0700, files 0600), and verify the tar SHA-256. The signing secret must stay on the server and must never be logged.
3. Install isolated exporter dependencies outside the application checkout: `@electric-sql/pglite@0.5.8` and `@electric-sql/pglite-tools@0.4.8`, with install scripts disabled. Set `PGLITE_RESCUE_TOOLS_ROOT` to that directory. Run `npm run test:recovery`; on Windows supply `TEST_BASH` for an available Bash-compatible executable.
4. Run `export-pglite-rescue.mjs export --snapshot PATH --sha256 SHA --output-dir NEW_DIRECTORY --tools-root TOOLS_DIRECTORY`. It restores the tar into a separate PGlite copy, exports complete SQL, restores that SQL again, and compares tables, data hashes, columns, indexes, constraints and sequences. The output SQL and manifest contain private application data and stay in protected server storage.
5. Check the reported source major. The verified PGlite version uses PostgreSQL 18. For Ubuntu 24.04, `bash ops/install-postgresql18.sh prepare --live-pid PID` verifies the official PGDG signing key, prepares a separate repository file and simulates a fresh installation. Review that result before the separate `install` invocation. The helper rejects upgrades/removals and suppresses service starts and restarts. Starting the new PostgreSQL service remains a separate operation.
6. Create a separately named, empty local database `white_gloss_recovery_SUFFIX`. Set its URL only as `RESCUE_TARGET_DATABASE_URL` in a protected server environment. The export helper never falls back to the application's DATABASE_URL.
7. Run `check-target --bundle DIRECTORY --expected-database NAME --pg-root PG_PACKAGE_ROOT`. Only after the empty-target/version check succeeds, import with `psql -X --single-transaction --set ON_ERROR_STOP=1 --file database.sql`, using protected connection configuration. Capture errors in a private log; SQL diagnostics can contain customer data.
8. Run `verify` with the same target arguments. Apply missing application migrations only after the comparison succeeds. Preserve the existing migration history, identifiers, Qonto mappings and sequence states. PostgreSQL crash recovery can advance sequences; do not reset them to MAX(id).
9. Before the final cutover, block incoming writes and drain requests without stopping the old Node process; also pause background writers. Take and seal a final snapshot, repeat export/import/verification against a fresh target, and prepare persistent runtime configuration. Activate only a release containing the booking-workflow compatibility contract. The legacy automatic-confirmation code cannot safely run against migration 0007.

The helpers do not publish a release, send notifications, create invoices, or remove the old database. Native import and live activation require explicit operational checks; the offline roundtrip alone does not certify a native PostgreSQL deployment.
